# opencode backend

[opencode](https://opencode.ai) 2.x as a codeoid backend (#447): one integration that opens opencode's 75+ model providers (GitHub Copilot, OpenRouter, Bedrock, Vertex, Azure, local Ollama, …) to sessions, routines and loops, with codeoid's approvals, spend caps and memory on top.

## Setup

1. Install opencode **2.2.5 or a later 2.2 release**. codeoid speaks the 2.x server API only (2.x replaced 1.x's API wholesale) and checks the version the server reports; anything else is refused with a message saying so, and the backend is taken off the picker. Earlier 2.2 releases are refused too: opencode 2.2.2 runs a shell command made only of redirections (`> file`) without asking anyone, so it could create or empty any file you can write. 2.2.5 asks for these.
2. Give opencode a model credential. Three ways:
   - **codeoid's own credentials** (see *Credentials* below). The keys codeoid has for its other backends reach opencode's providers: `ANTHROPIC_API_KEY` → `anthropic`, `OPENAI_API_KEY` → `openai`, `GOOGLE_API_KEY` (or `GEMINI_API_KEY`) → `google`; codeoid's Qwen backend on an API key → `qwen`; codeoid's OpenAI-compatible endpoints → `oai-<name>`.
   - **A stored sign-in.** opencode keeps sign-ins in its database, and codeoid's opencode has its own (below), so sign in against that one: `OPENCODE_DB=~/.codeoid/opencode/opencode.db opencode auth login`. That is the way for a provider codeoid has no key for (OpenRouter, Bedrock, GitHub Copilot, …). Don't run opencode's TUI on that database: approvals you save there ("always") would be rules codeoid never sees, so codeoid deletes any it finds.
   - **Your own opencode config.** The providers and models in your global opencode config (`~/.config/opencode/opencode.json[c]`) are carried in, and stand where codeoid configures nothing of that id. Name a key there with `{file:~/path/to/key}` (a relative `{file:…}` is read from that config's folder, as your own opencode reads it, never from a session's working directory). A key written there literally works too: like codeoid's own keys, each literal value of a carried provider is handed to opencode from a 0600 file in codeoid's credentials dir, never in the server's environment (which every process opencode starts, an MCP server's included, inherits). A provider with a value that has leading or trailing whitespace is left out, since opencode trims what it reads from a file. Left out, each with a line in the daemon's log: a provider whose `package` (or a model's) isn't one opencode bundles (`@opencode/ai/providers/…` or an AI SDK name opencode maps onto one, such as `@ai-sdk/openai-compatible`), since opencode would load it — a `file://` module, or one it installs from npm — into codeoid's server; a provider with an `{env:…}` reference, which would read the server's environment (no key is there); a provider with a value padded with whitespace (see above); and a `model` or `small_model` that isn't a `provider/model` id.
3. Pick it: `codeoid new <name> <dir> --provider opencode`, the web UI's backend picker, or `session.defaultProvider: "opencode"`.

```json
{
  "providers": {
    "opencode": {
      "enabled": true,
      "command": "opencode",
      "dbPath": "~/.codeoid/opencode/opencode.db",
      "dataDir": "~/.codeoid/opencode",
      "agent": "build",
      "model": "qwen/qwen3.8-max"
    }
  }
}
```

| Setting | Default | |
| --- | --- | --- |
| `providers.opencode.enabled` | `true` | Register the backend (it shows as unavailable, with the fix, when the binary is missing). |
| `providers.opencode.command` | `opencode` | Binary to run: a name on `PATH` or a path. |
| `providers.opencode.dbPath` | `opencode/opencode.db` beside codeoid's `dbPath` | opencode's database for codeoid's sessions. Relative paths resolve from codeoid's config dir. |
| `providers.opencode.dataDir` | `opencode` beside codeoid's `transcriptDir` | opencode's logs, shell output, state, caches and temp files (`data/`, `state/`, `cache/` under it: its XDG dirs; `tmp/`: its `TMPDIR`). Relative paths resolve from codeoid's config dir. |
| `providers.opencode.agent` | opencode's default (`build`) | The opencode agent sessions run: `build`, `plan` (read-only planning), or one of your own. |
| `providers.opencode.model` | opencode's default | The model, `provider/model`, of a session that doesn't pick one (`qwen/qwen3.8-max`, `anthropic/claude-sonnet-5`). With neither set, opencode picks its own default, which can be one of opencode's hosted free models that needs no key: the session's prompts then go to that service. A value with `{`, `}`, quotes, backslashes or spaces is refused: opencode would expand a `{file:…}` or `{env:…}` in it into the model id it sends with every request. |

All of them are in the web UI's settings (the *opencode* tab) and read when the daemon starts: change one, then restart the daemon. A key changed in codeoid's settings reaches opencode when its server next starts, too.

### Credentials

codeoid hands opencode its keys through opencode's config, never through the server's environment: opencode runs some shell lines without asking (only assignments, `cd`, `export`), so anything in that environment could end up in a result the model reads.

- Each key is written to a file only codeoid's user can read, one file per key (0600), in the daemon's own dir (`<namespace>-<pid>-<random>`, 0700) of `codeoid-credentials/` (0700) beside opencode's database. They are written when the server starts, and removed when it stops, dies or is refused. opencode reads them again each time it loads a location (a new workdir or worktree), so they stay while the server runs. Two daemons sharing a config (a second `codeoid start`, another port, a container or another host sharing the home) each have their own dir and never remove each other's; a daemon's start removes those of daemons that are gone (at the default database location too, and at every location a server of this config ran with, recorded in `opencode-locations.jsonl` beside codeoid's database: a moved `dbPath` leaves them behind), whether or not opencode is enabled or found then. Those locations' databases and key files stay refused to agents' file tools too. The record moves with codeoid's own `dbPath`: a location used before codeoid's database moved isn't covered. Whether a daemon is gone is told by its process only when it ran on the same host, boot and pid namespace; another's (a container's, another host's) is gone once its dir went a day without the heartbeat a running daemon gives it every 10 minutes. A daemon frozen for longer than a day (a paused container) can find its files removed: a new location its server loads then gets `wrong or missing API key` until the server restarts. Only the files codeoid writes there (`anthropic.key`, `oai-<name>.key`, …) are ever removed, never anything else and never recursively, and a symlinked dir is refused, never followed: a database kept in a project leaves the project's own files alone.
- The config codeoid injects names each file with opencode's substitution (`"apiKey": "{file:…/qwen.key}"`), which opencode 2.2.5 expands as it loads the config. The model and the session's shell never see the config.
- The server's environment carries no credential at all: no `*_API_KEY` or `*_API_TOKEN`, no provider-prefixed variables, no `CODEOID_AGENT_ENV_ALLOW` names, no codeoid tokens. It has what opencode needs to run: `PATH`, `HOME`, user, locale, CA trust, proxies that carry no credentials, and codeoid's own `OPENCODE_*` settings. A proxy URL with a user or password in it (`HTTPS_PROXY=http://user:pass@proxy:3128`) doesn't reach opencode, so behind an authenticated proxy opencode can't reach a hosted model; use a proxy that doesn't need credentials in its URL, or a local or `oai:` endpoint it can reach directly.
- Every backend's file tools are refused the credential files (every daemon's, in `codeoid-credentials/`) and opencode's database (which keeps stored sign-ins), as they are codeoid's own credential files: at the configured location and the default one, whether or not opencode is enabled or found.

| codeoid has | opencode provider | |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | `anthropic` | With `ANTHROPIC_BASE_URL` naming a gateway (as the Claude backend uses it), sent there (`<url>/v1`), never to Anthropic's API. |
| `OPENAI_API_KEY` | `openai` | With `OPENAI_BASE_URL` naming a gateway (as the OpenAI backend uses it), sent there. Not when codeoid's Qwen backend claims it (below). |
| `GOOGLE_API_KEY`, else `GEMINI_API_KEY` | `google` | `GEMINI_API_KEY` with `GOOGLE_GEMINI_BASE_URL` naming a gateway (as the Gemini CLI uses it) is sent there (`<url>/v1beta`). `GOOGLE_API_KEY` goes to Google, as the Gemini backend sends it. |
| The Qwen backend's default account (`codeoid account default <name> --backend qwen`) | `qwen`, OpenAI-compatible | The account's key and endpoint, as codeoid's own Qwen backend runs on them; `OPENAI_API_KEY` stays OpenAI's. An account that can't be used (removed) hands Qwen nothing. |
| Else the Qwen backend set up for a key: `providers.qwen` with a `baseUrl` (a preset such as `bailian-plan-intl`, resolved), a `model` or `authType: "openai"`, or a Qwen catalog codeoid has seen; no qwen.ai sign-in; and `OPENAI_API_KEY` (its endpoint `OPENAI_BASE_URL` when `baseUrl` isn't set) | `qwen`, OpenAI-compatible | Its models: `providers.qwen.model` and the Qwen catalog codeoid last saw. The key is for Qwen's endpoint, so `openai` doesn't get it. `OPENAI_BASE_URL` alone doesn't make it Qwen's. The gateway prices nothing: opencode reports its turns at $0 with tokens, which codeoid prices at your `pricing.models` price for the model (`qwen/<model>`), else counts as of unknown cost (see Cost). |
| An OpenAI-compatible endpoint (`oai:<name>`) with a model | `oai-<name>` | Its key and header values are files too. |

A provider codeoid configures replaces one of the same id from your own opencode config, base URL included: codeoid's key goes where codeoid sends it. A model id or name, or a base URL, that would itself make opencode substitute something (`{file:…}`, `{env:…}`) is never put in the config; that provider is left out, with its key. So is a built-in's key whose `*_BASE_URL` isn't an http(s) URL, and a key (a built-in's or Qwen's) whose gateway or endpoint URL carries a user, a password, a query string or a fragment (`https://user:pass@gw/`, `…?api_key=…`): the config is in the server's environment, which holds no credential. Put a gateway's credential in a header instead (an `oai:` endpoint), or use a gateway that takes the key alone.

## How it runs

- **One private server per daemon.** The first opencode session's first turn starts `opencode serve --stdio --port 0 --hostname 127.0.0.1`; every opencode session shares it. It listens on loopback only, with a fresh random password each start (HTTP Basic). If it dies, the next turn starts a new one and sessions resume; a subagent it was running when it died is gone with it, and is never shown as running again. It stops with the daemon — one still starting too: that start gives up, and its key files go — and can't outlive one: it exits when the pipe codeoid holds closes. It runs in an empty, read-only directory alone in a fresh root of its own (`codeoid-ocserver-…/cwd`, removed when it exits), never the folder of its database: a command can reach a process's working directory through `/proc/<pid>/cwd` (a session's shell is a child of the server, so `/proc/$PPID/cwd`), and every directory above it with `..`, which codeoid can't follow when the pid is only known as the line runs. So that directory holds nothing, and the root is made in the first of `/var/tmp`, `/dev/shm` and `/tmp` where no directory from it up to `/` holds anything of codeoid's: never the daemon's own temp dir, where codeoid makes its sign-in homes, nor beside codeoid's database, config, transcripts or opencode data, nor beside anything named `codeoid`/`.codeoid`. Where every one of them would, the server isn't started, and the turn fails saying why.
- **Never your own opencode.** Its database is codeoid's (`dbPath` above), so codeoid's sessions don't mix with yours, and so is its global config directory (`config/` beside the database). Your `OPENCODE_*` environment doesn't reach it, and nor do the daemon's keys (see Credentials). From your global opencode config (`~/.config/opencode/opencode.json[c]`) it takes only which providers and models you have (`provider`, `providers`, `model`, `small_model`, `enabled_providers`, `disabled_providers`; a provider loading a package opencode doesn't bundle is left out, see Setup); your plugins, agents, permissions, MCP servers and instructions there are not loaded. A repository's own opencode config is not read (`OPENCODE_DISABLE_PROJECT_CONFIG`), nor are `.claude` skills (`OPENCODE_DISABLE_CLAUDE_CODE`). Its logs, shell output, state, caches and temp files go to `providers.opencode.dataDir` (the server's `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and `TMPDIR` point into it), never to your own `~/.local/share/opencode`, `~/.local/state/opencode` or `~/.cache/opencode`, nor to a shared `/tmp/opencode`. The commands opencode runs for a session don't get those overrides: their environment is the bare one below, with your own XDG dirs and `TMPDIR`.
- **One opencode session per codeoid session**, in the session's working directory. Its `ses_…` id is the session's backing id: a daemon restart resumes it. opencode runs a session's tools where the session is, so a fork into a worktree of its own (or a session resumed in another directory) is moved there before it runs; one opencode won't move goes on in a new session there, from a transcript.

## What works

| | |
| --- | --- |
| Streaming | Reply and thinking stream as opencode writes them; each block ends in the session's history, so forks, backend switches, rewinds and routine summaries see the reply. |
| Tool cards and approvals | Every action opencode takes asks codeoid first (below). |
| Stop | Stop interrupts opencode's execution. Messages you sent mid-turn that opencode hadn't taken yet are withdrawn from its inbox, so the next turn doesn't get them. The same goes for a turn its budget (`maxBudgetUsd`, a routine's or loop's `--budget`) stops, which says a message wasn't run, and for an execution stopped from outside codeoid (opencode runs nothing after an interrupted execution): the turn ends there, saying the message wasn't run. If opencode's event stream is down when you stop, codeoid reads the turn back from the session before ending it, so the stopped call's card is settled and what the stopped step cost is counted in this turn. A step stopped while the model was still answering is billed nothing by opencode, so that turn's cost is unknown (`$?`, see Cost), and so is a turn stopped as opencode stores its prompt: opencode has often sent the step's request by then, and reports neither the step nor its spend. |
| Resume | A daemon restart, or a server restart, resumes the opencode session by its id. If opencode lost it, or it's deleted on the opencode server while in use (a turn running on it ends with an error), the conversation continues in a new one from codeoid's history. |
| Fork, rewind | A fork at a turn opencode ran forks opencode's own session there (nothing lost, reasoning included). Otherwise — a turn from another backend, a rewound history — opencode gets a transcript. Files are codeoid's checkpoints, as on every backend. |
| Models and effort | The picker lists opencode's models with a credential (`provider/model`), each with its context window; a model's reasoning variants named like codeoid's levels (`minimal` … `max`, `none` = Off) are its efforts. Model and effort are switched on the session before a prompt when they changed. opencode keeps the effort on its session, across restarts too, so a session resumed on a higher effort goes back to the model's default when you reset it. |
| Cost | opencode reports the dollar cost and tokens (input, output, reasoning, cache read and write) of every step: a step stopped after the model answered bills what it used; a request the provider refused (a 400, or a 429 or 5xx after opencode's own retries) bills nothing, and so does one never sent because the model's endpoint couldn't be reached (a refused connection, an unknown host), as long as nothing of an answer came; a connection reset or a timeout may come after the request was served, so it doesn't count as nothing (below). opencode's retries show as retries, the first one numbered 1. Each turn carries their sum, subagents' included, and what opencode bills without a step — the title it writes for a session's first prompt, each request of a compaction — which codeoid takes from opencode's running total, read as each turn ends (opencode books the title just after the reply ends), each once. So spend caps count real spend, and a routine's cap stops the turn as the spend lands, not only between turns; a step opencode reports at $0 with tokens counts toward that cap at your `pricing.models` price for the `provider/model` id of the model that step ran on (a subagent's own, which can differ from the session's), and with no such entry the capped turn stops at it: the list-price snapshot is keyed by bare model ids (`claude-sonnet-4-5`), so it never prices an opencode id (`anthropic/claude-sonnet-4-5`). That figure is opencode's own: codeoid doesn't price its tokens again. Where part of a turn's spend went unreported, the turn's cost is **unknown** (`$?`), never $0, and a routine with a spend cap stops on it: a step stopped while the model was still answering (opencode bills it nothing), an attempt whose response broke off after part of an answer and that opencode then retried (a stream that ended early, a connection reset mid-reply: opencode fails it with the response's own 200 status and bills it nothing, though the request was served), a step that reported no usage, one still running when the server or the session went away, a compaction stopped while its summary request was streaming (opencode records nothing for that request, though it was sent with the whole conversation), an execution stopped before it announced a step (an interrupt as the prompt is stored: the request has often gone out, and opencode reports nothing of it), or a dropped connection whose gap couldn't be read back. A $0 with tokens isn't a price (a subscription sign-in, a model opencode's catalog prices at $0, a provider configured without a cost): a turn of only such steps is priced as codeoid prices tokens, at your `pricing.models` price for the `provider/model` id, else unknown; one mixing them with priced steps is unknown. A failed turn reports what it spent itself, once. |
| MCP | codeoid's memory, the goal blackboard, the registry's servers and its OAuth servers (through the daemon's relay) are mounted for the session. Memory recall is auto-approved as on other backends. |
| Subagents | opencode's subagents show as subagents, their calls ask codeoid like the main agent's, and their spend counts — one the model sends a follow-up to later, by its id, too, after a restart. A background subagent shows as background work; when it finishes, opencode hands the result to the model and answers, and codeoid shows that turn. Switching the session's model, or anything else that restarts its backend (an MCP or sign-in change), stops its subagents and its background shell commands, as on other backends: a request one had waiting is refused, and so is the turn opencode starts to report a stopped one. If such a turn still runs when the session is next used, codeoid stops it first, so the new message isn't left queued behind it. |
| Commands and skills | opencode's own slash commands `/init` and `/review`, the prompts of the session's own MCP servers (`/<server>:<prompt>`) and opencode's skills are listed in the command palette and run with `/name args`. Commands from a config directory (`commands/*.md`, in `/etc/opencode` say) are not run as commands: opencode runs every `` !`…` `` of their template through the shell, your arguments substituted in, without asking anyone. A message naming one goes to the model as text, as does one naming a built-in that such a command replaced, or a built-in whose arguments hold `` !` ``. |
| Questions | opencode's questions (its forms) are asked through codeoid's dialogs; dismissing one tells the model you didn't answer. A question opencode settles itself — its call ended: a budget stop, a stopped subagent — closes its dialog everywhere. |
| Messages mid-turn | A message sent while opencode works steers the running turn (opencode takes it at the next step); one sent as "later" is answered after the current reply, in the same turn. One sent before the turn's prompt reached opencode goes after it. If the model request fails while such a message waits, opencode still answers the message next; the turn shows the error first. One sent just as the turn ends, before codeoid showed its end, or while a Stop you gave is still settling, starts a turn of its own. |
| Dropped connection | codeoid follows opencode on one live feed. If it drops, what happened meanwhile is read back from opencode when it reconnects: the running turn's text, steps, results and end; subagents started in the gap (their requests are then asked), and how each subagent went; and a turn opencode ran by itself in the gap (a background subagent's result), which is shown as a turn of its own. |
| Agent | `providers.opencode.agent` picks the opencode agent sessions run. |

## Approvals

codeoid owns the policy, so opencode is set to ask about every action and never settle one itself:

- Every codeoid session (and every child session a subagent starts) gets the rule *ask for everything*, last, so nothing an opencode agent allows survives it. The injected config says the same globally.
- opencode documents that a subagent uses its own permissions, and its built-in `explore` subagent allows shell commands. When the server starts, codeoid reads every agent's rules; if a subagent would act without asking, codeoid restarts the server once with overrides that turn those allows into asks, and refuses to use a server where one remains.
- codeoid answers each request once (`once`) or rejects it with the reason, which the model reads and carries on from. It never answers "always".
- Paths are shown as they really resolve. opencode asks about a directory outside the session's working directory only when the path as written is outside its boundary — the working directory, or the whole git checkout it's in (a monorepo's root, or a home directory kept in git) — and reads and writes through a symlink inside it without asking; so a read or search that really reaches outside the working directory is asked as `opencode_external_directory`, which is never approved on its own (`Read`, `Glob` and `Grep` are, in guarded mode), unless you just approved opencode's own question about that directory for the same call. A write names the file it really changes. A path that goes through a link whose target depends on the process following it — `/proc/self`, `/proc/thread-self`, `/dev/fd`, `/dev/stdin` and the like, or any other link on procfs (a process's `cwd`, `root`, `fd/N`) — is refused without asking, whether as written or through a symlink in the working directory: codeoid would resolve it in its own process, but opencode follows it in its own, where `/proc/self/cwd` is the server's own directory. Every path in a call — a read, search, edit, write or patch target, a shell's working directory, a directory card — is judged the same way: resolved as the kernel resolves it in opencode's process, one component at a time, with `..` taken after following whatever came before it (so a link whose target goes up out of another link's target, such as `out/../file`, is shown where it really lands). A path that can't be resolved for certain — `..` after a component that doesn't exist, a path that leads somewhere different as written than as opencode reads it (opencode collapses `..` before following links), one under a file or that codeoid can't look at, a link loop — is asked as `opencode_unresolved_path` with the reason and every place it might lead, in every mode, autonomous included; it is refused if one of those places holds credentials, and under a read-only capability role (it may be a write). A shell command in such a call is judged by risk in each of those places, the worst counting: its card shows the level, and a credential read is refused as anywhere. A path in a tool's input that starts with `~/` (or is `~`) is opencode's home, the daemon's own `HOME`, as opencode reads it: `~/.codeoid/config.json` is refused like its absolute form, and the directory card (`opencode_external_directory`) is judged by the secret-path gate too, so one reaching codeoid's config dir is always asked. A patch (the tool opencode gives GPT-family models instead of edit and write) is one card for every file it changes; each of them is judged, so a patch that changes a credential file anywhere in its list is refused.
- Cards show a call's input as the tool gets it. opencode repairs a model's input before the tool runs (a stringified object is parsed, `"true"` and `"20"` become `true` and `20`), so a `background: "true"` shell is shown as a background one, and a glob whose path is `"undefined"` or `"null"` is shown searching the working directory, as opencode's glob runs it; a flag holding anything opencode wouldn't read the same way is refused unasked. A call whose arguments the model sent as one JSON string (opencode announces it as `{ "value": "<the json>" }` and runs the object it holds) is shown as that object. Where a glob or grep searches is taken from opencode's own request, which says what the tool runs; a call that says otherwise is refused unasked, and so is a write, an edit or a subagent whose card would be missing what it writes, changes or is told.
- A fetch stays on the site you approved. opencode follows a fetch's redirects itself and asks about none of them, so while an approved fetch runs its session refuses every other site: a redirect to another site fails the call (the model can fetch the new address, which asks again), and one on the same site (`http` to `https` excepted, which is another site) is followed. A fetch of another site that starts while one runs in the same session is refused too, and the model can try it again.
- A shell line with no command in it — only `cd`, variable assignments, `export` / `unset` / `readonly` of names, comments, and in the session's own shell a declaration builtin given only options or nothing (`export -p`, `declare -p`, `unset -v X`, `local`), which lists the shell's own variables — runs without asking: opencode 2.2.5 asks about a shell line only when it finds a command in it. codeoid shows it as a card that ran without asking; such a line rates medium at most (low if it is only a comment), never one the risk rating would ask about in every mode or refuse. A comment runs nothing whatever it holds, so a `$(…)` in one doesn't count. Such a line can still print a variable it expands (`X=${UNSET?$VAR}`), so each session's shell, and each subagent's, runs with a bare environment: `PATH`, `HOME`, user, shell, terminal, temp dir, locale, CA trust, proxies that carry no credentials, and the daemon's own XDG base dirs (yours, not the server's). The server's password and the config codeoid injects are the server's, not the shell's; model keys are in neither environment. A line with `$` in it, or anything else that ran unasked, still stops the server (below); so does a listing a subagent runs unasked, since a subagent whose start fell in a feed gap may still have the server's environment (see Known gaps).
- Anything that can't be shown faithfully is rejected without asking: an action codeoid doesn't know (a plugin's, an MCP server codeoid didn't mount), another session's MCP mount, a shell request without its command. A request still waiting when the server goes away counts as rejected.
- The tools that act without asking (opencode's session rename/move, worktree and schedule tools) are turned off.
- No plugin but opencode's own runs: a plugin can settle a request itself, so opencode would never ask codeoid. Your global plugins aren't loaded (above); a server that lists any other (from opencode's system config directory, say `/etc/opencode`) is refused when it starts and before every turn, and if opencode ever runs a call without asking codeoid (other than a shell line with no command in it), codeoid stops the server and the turn ends saying so. The other sessions on the server are told only that codeoid restarted it.
- Code Mode (opencode's `execute` tool, which runs a script that calls tools and `fetch`) is turned off: on opencode 2.2.2 a script's `fetch` reaches any URL without asking anyone. opencode's browser tools stay off too, as opencode's own agents have them.

| `question` | `opencode_question` — then the questions themselves |
| `external_directory` | `opencode_external_directory` |
| any call with a path codeoid can't resolve for certain | `opencode_unresolved_path` (`tool`, `path`, `paths` it might lead to, `reason`, `call`: the tool's input) — always asked |

Because every call reaches the gate under these names, a pipeline phase's capability role is enforced on opencode, as on Claude.

## Limits

- **Your own opencode MCP servers and plugins aren't loaded.** Mount servers through codeoid's registry instead (`mcpServers` in codeoid's config); they reach opencode and every other backend.
- **The private server is private from other users, not from your own processes.** opencode takes its password only from its environment, which any process running as the daemon's user can read (`/proc/<pid>/environ`) — including a command you approved. Such a process can drive the server directly, outside codeoid's gate and audit, and read the keys opencode holds: its API returns its configuration with each `{file:…}` expanded (`/api/config`, `/api/provider`, `/api/model`), and lists stored sign-ins with their secrets (`/api/credential`); the same process could read the key files anyway. Nothing the model or a shell line that runs without asking can read holds a key. codeoid re-applies each session's rules and deletes saved "always" approvals before every turn, and stops a server that ran anything without asking, but it can't keep the password from your own user. To separate them, run the daemon as a dedicated user.
- **A question asks twice in guarded mode**: once to let opencode ask, then the question.
- **Known gap: a subagent's first moments.** opencode doesn't give a subagent its parent's shell environment; codeoid sets the bare one as it learns of the subagent, from opencode's live feed. If that feed drops just as a subagent starts, the subagent's shell has the server's environment until the feed is back. That environment holds no model key, but it does hold the server's password and the config codeoid injects (which names the key files, not their contents, and carries your own opencode config's provider and model keys as written). A line with no command in it (`X=${UNSET?$OPENCODE_PASSWORD}`) runs unasked and can print one into the subagent's result, which its parent's model reads; using the password takes a command, which asks. codeoid reads back what ran in the gap and stops the server when it finds such a call, failing the turn, and shows nothing of the call's output, but by then the line has run. Keep literal keys out of your own opencode config (use `{file:…}`) so it holds none.
- **Commands opencode runs don't see the daemon's credentials.** The shell's environment is bare (see Approvals), so a command that needs a token or a cloud key has to get it from its own configuration (`gh auth login`, `~/.aws/credentials`), as it would for a user without those variables.
- **codeoid accounts don't apply** (`codeoid account …`), except the Qwen backend's default account: opencode's credentials are the daemon's keys, its Qwen backend's and its endpoints' (see Credentials), and opencode's own sign-ins. A key for a provider codeoid doesn't map (OpenRouter, Bedrock's `AWS_*`) doesn't reach opencode from the daemon's environment: sign in in codeoid's opencode database instead.
- **Another backend's history reaches opencode as a transcript**, not as opencode messages.
- **`/goal` isn't run as a command.** opencode's goal loop asks the model to review the work after every round (up to 50), and opencode reports that spend nowhere: not in a step, not in the session's total. codeoid couldn't show it in the turn's cost nor stop it at a budget, so a `/goal …` message goes to the model as text.
- **A turn opencode prices at $0 is of unknown cost** unless you price its model. opencode reports a subscription sign-in's turns (ChatGPT, GitHub Copilot) and a free model's at $0, which isn't what they cost elsewhere; so they show as `$?` and stop a capped routine. To count such a model as free, price it in `pricing.models` under its opencode id, e.g. `"github-copilot/claude-sonnet-4.5": { "input": 0, "output": 0 }` ([Model prices](CONFIGURATION.md#model-prices)).
- **Not in opencode 2.x:** language-server diagnostics and session sharing.
- **Not yet:** a codeoid-wide plan mode (opencode's `plan` agent is reachable through `providers.opencode.agent`), an agent picker, quick questions that don't enter the conversation, manual compaction (codeoid has no compact action yet), and a view of the files a step changed.

## Troubleshooting

- *opencode is unavailable: no opencode binary found* — install it, or set `providers.opencode.command`.
- *opencode X is installed, but codeoid supports opencode 2.2.5 or a later 2.2.x* — install 2.2.5 or a later 2.2 release (2.2.0 to 2.2.4 are refused, see Setup).
- *opencode agents … would run tools without asking codeoid* — an agent's rules allow tools in a way codeoid's overrides can't reach. Remove it from opencode's system config directory (`/etc/opencode`).
- *opencode runs plugins codeoid doesn't know* — a plugin in opencode's system config directory, or in codeoid's own opencode config dir (`config/` beside its database), which codeoid never writes. Remove it there.
- *opencode ran … without asking codeoid* — something settled a permission request itself; codeoid stopped the server. The next turn starts a new one, checked again. Turns of other sessions that were running on it end with *codeoid restarted the shared opencode server*; send them again.
- *No models in the picker* — opencode lists only models it has a credential for; see Setup. The daemon's output says which of codeoid's credentials it left out and why (`not handed to opencode: …`), say a Qwen key with no model.
- *A session runs a model you didn't pick* — with no model chosen, opencode uses its own default, which with no credentials set up is one of opencode's free hosted models (on opencode.ai). Pick a model, or set one in your opencode config.
- opencode's own log is in `<dataDir>/data/opencode/log/`. To see what it says about your configuration interactively, run `opencode serve` by hand with the same `OPENCODE_DB` and `OPENCODE_CONFIG_DIR`.
